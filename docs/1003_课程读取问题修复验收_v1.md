## 保存与统计口径

网页默认回溯 7×24 小时，Python 使用配置 `lookback_days`。公告请求起止与各自窗口一致，按 posted_at、缺失时 created_at 筛选；文件按创建时间筛选，新资料里的“有更新”只标记该窗口内新建文件的后续修改，不是所有历史文件最近修改的检索。待办范围保持现有逻辑，未宣称修复 Issue #4 的 CS5222 漏同步。

列表完全读完为 coverage=all；文件提前证实窗口完整为 coverage=window；预算、循环、异常地址等为不完整，不能当成功空列表。若无旧内容而有部分已读条目，显示这些条目但明确未完整读取；若有可用旧内容，优先显示并标记旧内容及原时间。真实成功空列表才替换旧列表为空。

同日记录仍替换该日记录，其他历史保留原流程；失败部分附带旧时间，作业成功才更新其快照。更换凭证 / 配置时不复用绑定不同的快照与可选旧数据；旧版无绑定历史无法证明账号身份，用户换账号前仍需备份并清除旧历史。旧记录没有精确状态和 UTC 时间时不伪造，采用原时间或“未知”。

可选失败并已保存可用数据为部分成功；提醒的成功时间指关键课程 / 作业和保存完成，不指所有可选内容。网页存储失败尽力回滚；Python 多份产物仍逐份写入，不提供跨文件原子事务保证，磁盘故障可能造成部分产物已更新，需核对实际输出。这是已有保存架构的限制，本次未做无关重构。

## 用户如何测试 / 更新自己的 Worker

本次仅本地准备，GitHub 的现有 v2.2 附件尚未包含修复。审阅后测试应使用当前项目生成的完整 `worker.js`，不要复制 runtime 源码片段；此报告不表示已经替用户部署。

1. 在原个人看板“设置 → 备份”导出历史。保持同一 Worker 正式网址与浏览器，方便核对旧数据保留。
2. 登录自己的 Cloudflare，打开自己的原 Worker 编辑器，全选旧代码，替换为本项目 `worker.js` 全文，点击 Deploy。无需新增 KV、Cron、SendKey，也不操作作者服务器。
3. 打开 Worker 的正式网址，重载后点击“刷新课程”；仅检查连接不代表公告和文件已读取成功。Token 自己在设置中填写，不发进聊天。
4. 完整成功应显示已更新；部分成功应显示文件 / 公告成功门数，展开查看具体课程与 HTTP 类别，课程卡片能看到旧时间或未完整读取。明确权限 403 不反复换 Token，先核对学校课程页面。
5. 在同日再次刷新，对比旧资料是否带保留标记、作业是否仍正常、公告 404 是否消失；反馈脱敏课程名、错误类别与时间即可，截图不包含 Token、认证头或个人 Worker 密钥。

本地 Python 测试则用已有同一个 Python 3.8+ 环境，在本地填写配置后先 `--check-config`，再运行引擎，检查 `OK` / `PARTIAL_OK` / `FETCH_FAILED` 和周报。它直接查询学校，不需要 Worker；`github.push_enabled` 保持 false。
