# 手动刷新与三天提醒开发提示词 · v1

日期：2026-10-02。按用户最新想法调整为“手动刷新 + 每三天提醒”，本次只生成提示词，不修改系统功能。

## 推荐交互

| 情况 | 用户看到什么 | 程序行为 |
|---|---|---|
| 随时想更新 | 顶栏“刷新课程”按钮 | 用户点击后查询 Canvas，更新看板 |
| 距上次成功更新超过三天 | “课程数据已超过 3 天未更新”及“刷新课程 / 暂不刷新” | 只提醒，不自动抓取；继续显示旧看板 |
| 选择暂不刷新 | 保留上次更新日期 | 收起当次提醒，不覆盖数据、不发请求 |
| 不需要提醒 | 设置中关闭“更新提醒” | 仍可随时手动刷新 |
| 页面关闭 / 设备休眠 | 不承诺定时通知 | 下次打开或恢复可见时检查数据时间 |

现有顶栏已经有 refresh-btn（🔄），优先改成清楚的“刷新课程”，复用同一逻辑，避免重复入口失去同步。三天指距上次成功更新满 72 小时，不是“每第三个自然日”或自动后台作业。

- 历史 [Issue #1](https://github.com/Famalhaut04/canvas-weekly-hub/issues/1) 是 KV 教程，[#2](https://github.com/Famalhaut04/canvas-weekly-hub/issues/2) 是离线下载入口，[#3](https://github.com/Famalhaut04/canvas-weekly-hub/issues/3) 是网络连接；核对时均 CLOSED。新功能不恢复 KV 或云端订阅。
- 浏览器后台计时有执行限制；本方案只在打开 / 恢复页面时检查是否过期，参见 [Chrome 官方说明](https://developer.chrome.com/blog/timer-throttling-in-chrome-88/)。

## 可复制给 Codex 的提示词

```text
请为 Canvas Weekly Hub v2.2 增加“手动刷新 + 每三天更新提醒”，让用户自行决定是否查询 Canvas。

项目目录：
D:\GitHub\Projects\canvas-weekly-hub

先读取 README.md、docs/网页版使用指南.md、docs/系统概述.md、docs/部署指南.md、web/overrides.js、web/build_web.py、site-template/index.html、worker/runtime.js、canvas_weekly_report.py、serve_board.py 及现有测试，按实际实现完成改动。

一、交互目标

1. 保留并改进现有顶栏 refresh-btn，把仅图标的“🔄”改成清楚的“刷新课程”，沿用现有风格，桌面和手机都能找到。
2. 不添加第二套独立刷新逻辑。按钮真正查询 Canvas、更新看板与快照，不能只是 location.reload() 或重新显示缓存。
3. 显示“上次成功更新：具体时间”。用户可随时点击刷新，不必等三天。
4. 距上次成功更新满 72 小时时，在看板显示温和提示：
   “课程数据已超过 3 天未更新，是否现在刷新？”
   按钮：“刷新课程”“暂不刷新”。
5. 只提醒，绝不因提醒到期而自动请求 Canvas。选择暂不刷新保留旧看板与历史，收起本次提醒；同一次页面使用中不反复弹出，重新打开时可重新检查。
6. 设置中提供“更新提醒”开关，默认开启三天提醒；可设置正整数提醒天数，默认 3 天，至少 1 天。关闭提醒不影响手动刷新。
7. 提醒、看板和设置统一显示当前选择的天数，不能修改间隔后文案仍写“三天”。使用设备时区显示时间，以时间戳计算经过时长。
8. 本轮不开发自动抓取模式。不得把“三天提醒”写成“三天自动刷新”，不新增通知权限、邮件、微信、云端订阅或 Cron。

二、时间与状态

- 新增可靠的上次成功更新时间戳，只有成功完成关键课程 / 作业读取及保存数据后才更新。
- 配置保存、页面重新打开、点击暂不刷新、请求失败不能更新该时间。
- 现有历史可能只有格式化的 updated_at；核对格式与时区，安全迁移。无法可靠解析时显示“更新时间未知，可手动刷新”，不要假装刚更新或擅自发请求。
- 页面打开、重新可见、从休眠恢复时检查过期。可见页面跨过提醒阈值时也能显示提示，不依赖精确后台定时运行。
- 关闭页面不会继续查询或保证收到提醒；下次打开再判断是否超过间隔。
- 暂不刷新只处理提示的显示，不更改抓取成功时间、不清理课程数据。
- 提醒设置仅保存在当前浏览器，换浏览器 / 网址 / 设备不自动同步；清除本地数据时一并清除相关状态。
- 计划设置只保存自己的字段，不能意外保存正在编辑且尚未验证的 Token。

三、复用刷新与失败保护

- 复用 fetchAll、withHubTask、boot 与现有手动刷新逻辑，防止连续点击或多个入口发起重叠请求。
- 同源多个标签页可同时提示，但要协调用户点击后的请求，避免多页重复抓取；不广播 Token 或课程正文。
- 刷新中显示状态并禁用重复点击，结束后恢复按钮。
- 关键请求失败保留旧配置、看板、快照与成功时间；课件 / 公告部分失败可保存可用结果，但明确警告。
- Token 无效 / 过期、学校权限、Worker 服务和网络不可达分别提示，不能统称“连接失败”。
- 存储失败不宣称保存成功，不无限重试，不反复弹窗打断阅读。
- 刷新按钮与更新提醒不得误提交 Token 草稿；成功更换学校 / 账号后重新绑定提醒状态，不能沿用另一身份的时间。
- 基础版查询仍经自己的 Worker，不经过作者服务器。升级版保留本地 Python / agent 路线；如调整本地刷新按钮，同样复用已有 /refresh，离线 HTML 不主动查询。
- 不新增 KV、Cron、SendKey 或云端凭证存储，github.push_enabled 保持 false；不把 Token 输出到聊天、日志、URL、截图或 Git。

四、单独排查 Issue #4，不能用刷新替代正确性

读取：
https://github.com/Famalhaut04/canvas-weekly-hub/issues/4

用户三张截图显示：
- 助手待办有 8 项，没有 CS5222；有超过七天后截止的任务，也有已提交任务。
- 学校 CS5222 作业页有 Assignment 1（10 月 9 日 23:59）、Research report（11 月 20 日 23:59）、Wireshark assignment（11 月 27 日 23:59）。
- 助手 CS5222 卡片已有课程与四项资料，不能说整个课程没获取，也不能据此证明作业接口成功。

核对原始作业获取 → 分页 → 筛选 → 保存 → allTodo 去重 → 渲染：
1. fetchAll 读取最近 7 天新增 / 更新和未来 7×24 小时截止任务。
2. allTodo 合并 upcoming 与仍有未来截止日期的 new_assignments，所以近期新增但远期截止的任务可以显示。
3. 早已发布且远期截止的未提交任务可能持续不显示；多刷新不会自动修复这个范围问题。
4. 当前待办也会包含已提交任务，并非“全部未提交作业”视图。
5. 检查个人截止时间、课程 / 历史周选择、无截止及逾期未提交、同名跨课和缺失 URL 的去重。
6. 用虚构课程与作业证明代码行为；没有真实 API 返回时标为待验证，不认定 CS5222 的根因。
7. 若确需增加“全部未提交作业”视图或改变范围，另给最小修复方案，不擅自与提醒频率合并。不要要求用户提供真实 Token，不自行回复或关闭 issue。
```
